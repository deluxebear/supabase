# pg_durable 0.2.8 Studio UI improvements — design

Date: 2026-10-01
Branch: `custom/main` (fork)
Builds on: `d63e166fb2` (integration entry) and `71a4bbc2c9` (workflow management UI)

## Goal

The Studio pg_durable integration currently covers a subset of the extension: leaf steps
(`sql`, `sleep`, `signal`, `http`) composed sequentially or in parallel, a flat step list in
the detail sheet, and a small runtime configuration page. pg_durable 0.2.8 exposes much more:
loops with `continue_on_failure`, conditionals, races, cron waits, multipart HTTP,
independent-transaction starts, `df.explain`, and several new GUCs.

This work brings the Studio UI up to the 0.2.8 feature surface while keeping older
installations usable.

### Decisions already made

- Scope: builder control flow, detail sheet tree + fixes, runtime configuration GUCs, start
  options, and **re-run**.
- Builder nesting: **two levels**. Top level is a step list; a step may be a container whose
  body is a list of leaf steps. Deeper nesting goes through expression mode.
- Version handling: **gate by version**. Read `df.version()`; features above the installed
  version are disabled with an "upgrade required" tooltip.
- Verification: unit tests + typecheck + lint. No live 0.2.8 instance is available, so there
  is no browser end-to-end pass.

### Non-goals

- Unlimited container nesting in the builder.
- Running `ALTER EXTENSION pg_durable UPDATE` from Studio (copy-only command).
- Editing GUCs from Studio (read-only; most require a restart).
- 0.2.9 features (`df.with_http_options`, `df.endpoint`, `df.secret`, `http_security`).
- Variable (`df.setvar`) management UI.

## 1. Data layer (`apps/studio/data/pg-durable/`)

### Version capabilities

New pure function `getDurableCapabilities(version: string)` in `pg-durable.utils.ts`:

| Capability              | Minimum version |
| ----------------------- | --------------- |
| `multipart`             | 0.2.5           |
| `transactionMode`       | 0.2.5           |
| `loopContinueOnFailure` | 0.2.8           |
| `logWorkflowSql`        | 0.2.8           |

Parses `major.minor.patch` (ignores pre-release suffixes). An unparseable version returns all
capabilities `false`. Unit-tested.

### Configuration query

Extend `getConfiguration` and `durableConfigurationSchema` with:

- GUCs, each read via `current_setting(name, true)` so a missing GUC is `NULL`:
  `log_workflow_sql`, `host`, `max_new_transaction_starts`, `new_transaction_start_timeout`,
  `list_instances_max_limit`, `enable_superuser_instances`, `max_user_connections`,
  `max_management_connections`, `max_duroxide_connections`, `execution_acquire_timeout`.
- `installed_version` from `pg_extension.extversion` and `default_version` from
  `pg_available_extensions` (pending `ALTER EXTENSION ... UPDATE` detection).
- `can_explain`: `has_function_privilege(current_user, 'df.explain(text)', 'EXECUTE')`.

New schema fields are nullable so old installs parse.

### Detail query

- `info` gains `created_at`, `completed_at`, `submitted_by` (text), `database` via a
  `LEFT JOIN df.instances` (RLS-scoped, same visibility as `df.instance_info`) and the
  `root_node` id (needed for tree building and re-run).
- `nodes` gains `inferred_status_from_ancestor_id`.

### Explain query

New `durableExplainQueryOptions({ input })` running `SELECT df.explain(${literal(input)})`.
Used both for a DSL expression (preview) and an 8-hex instance id (plan tab). Not polled;
`staleTime` 0 for previews, refetch on demand.

## 2. Builder: two-level nested model

### Form model

```ts
type LeafStep =
  | { type: 'sql'; query; resultName }
  | { type: 'sleep'; seconds; resultName }
  | { type: 'signal'; signal; seconds; noTimeout; resultName }
  | { type: 'http'; url; method; body; headers; timeoutSeconds; resultName }
  | { type: 'multipart'; url; method; parts; headers; timeoutSeconds; resultName } // ≥ 0.2.5
  | { type: 'schedule'; cron; resultName }
  | { type: 'break'; value }

type ContainerStep =
  | { type: 'loop'; condition; continueOnFailure; body: LeafStep[]; resultName } // continueOnFailure ≥ 0.2.8
  | { type: 'if'; condition; then: LeafStep[]; else: LeafStep[]; resultName }
  | { type: 'if_rows'; rowsResultName; then: LeafStep[]; else: LeafStep[]; resultName }
  | { type: 'race'; body: LeafStep[]; resultName } // each body step is a branch, ≥ 2
  | { type: 'parallel'; body: LeafStep[]; resultName } // each body step is a branch, ≥ 2
```

RHF needs a single flat field shape per array item, so the stored form value keeps the
existing pattern: one object with every field, discriminated by `type`, validated with zod
`superRefine` per type. Container children use the same leaf shape. Top-level
`composition: 'sequential' | 'parallel'` stays.

Validation rules (in addition to existing ones):

- `signal`: `seconds` required unless `noTimeout`.
- `http` / `multipart`: `timeoutSeconds` whole number 1–3600, default 30.
- `multipart`: `parts` is a JSON array of objects with string `name` and `data_b64`, optional
  string `filename` / `content_type`.
- `schedule`: five whitespace-separated cron fields, each matching `[0-9*,/-]+` (server
  performs full validation; the client check catches obvious mistakes).
- `break`: empty, or valid JSON.
- `loop`: body ≥ 1 step; `continueOnFailure` rejected when the capability is missing.
- `if`: condition required; `then` ≥ 1 step; `else` may be empty.
- `if_rows`: `rowsResultName` matches the identifier regex; `then` ≥ 1 step.
- `race` / `parallel`: body ≥ 2 steps.
- `break` is only allowed inside a `loop` body (top-level `break` is a validation error).
- Total leaf steps ≤ 60.

Capability-gated options are validated against capabilities passed in through the resolver
context, so a stale form cannot submit a gated feature.

### SQL generation

All generation stays in `Durable.utils.ts` using `safeSql` + `literal`, no string
concatenation:

| Step                | Output                                                                  |
| ------------------- | ----------------------------------------------------------------------- |
| `signal` no timeout | `df.wait_for_signal(name)`                                              |
| `http`              | `df.http(url, method, body, headers::jsonb, timeout)`                   |
| `multipart`         | `df.http_multipart(url, method, parts::jsonb, headers::jsonb, timeout)` |
| `schedule`          | `df.wait_for_schedule(cron)`                                            |
| `break`             | `df.break()` / `df.break(value)`                                        |
| `loop`              | `df.loop(body[, condition][, continue_on_failure => true])`             |
| `if`                | `df.if(condition, then, else)`; empty else → `df.sql('SELECT NULL')`    |
| `if_rows`           | `df.if_rows(name, then, else)`; empty else → `df.sql('SELECT NULL')`    |
| `race`              | left fold of `df.race(a, b)`                                            |
| `parallel`          | left fold of `df.join(a, b)`                                            |

Container bodies (`loop` body, `if` arms) are sequenced with `df.seq`. `resultName` on any
step wraps with `df.as(...)`. Condition SQL is passed through `literal()` (auto-wrapped by
pg_durable).

### Start options

- `transactionMode: 'caller' | 'new'`, shown only when the capability is present. Description
  explains rollback survival and the `max_new_transaction_starts` admission cap (value read
  from configuration).
- `buildStartWorkflow(expression, label, transactionMode)` emits
  `df.start(expr, label, NULL, transaction_mode => 'new')` only for `'new'`; the caller path
  stays byte-identical to today.

### Explain preview

"Preview plan" button in the sheet footer area, for both builder and expression modes, when
`can_explain`. Builder mode explains the generated expression; expression mode explains the
raw text (`acceptUntrustedSql`, same trust model as submit). Output renders in a monospace
block; SQL errors render inline with `AlertError`. The existing generated-SQL preview stays.

### Components

- `WorkflowStepFields` → split into `LeafStepFields` (existing leaf fields + new leaf types)
  and `ContainerStepFields` (container settings + one `useFieldArray` per child list,
  rendered with `LeafStepList`).
- `CreateWorkflowSheet` accepts optional `initialValues` (used by re-run) and the capability
  set.
- Follow the `react-hook-form` and `studio-ui-patterns` skills (no `watch()` in render, use
  `useWatch`; `FormItemLayout`; reset semantics).

## 3. Detail sheet

### Step tree

Pure function `buildNodeTree(rootId, nodes)`:

- Children come from `left_node`, `right_node`, and, for `IF`/`LOOP`, `condition_node` in the
  `query` JSON; for `JOIN`, `extra_nodes`.
- Root: `info.root_node`, falling back to the node no other node references.
- `THEN` chains are flattened into one ordered sequence so long workflows don't nest deeply.
- Children are labeled by role: `condition`, `then`, `else`, `body`, `branch N`.
- Cycles and missing references are tolerated (rendered as an "unknown step" leaf), never
  thrown.

Rendered as indented collapsible rows (existing `details` styling), each showing node type
badge, result name or node id, and status.

### Status and metadata

- `inferred_status === 'skipped'` gets a neutral badge plus "Skipped because step {{id}}
  decided this branch won't run" when `inferred_status_from_ancestor_id` is set.
- Loop generation is parsed from `status_details.execution_id` (last `::` token) and shown as
  "Iteration N" for nodes inside a loop.
- **Bug fix:** `status_details` is no longer rendered as red error text. When the node status
  is `failed`, the error comes from `result`; `status_details` is shown in a collapsed
  "Metadata" JSON block.

### Header

Adds created at, completed at, submitting role, and database. Adds a "Plan" section with
`df.explain(instance_id)` output (loaded on expand, refetch button).

## 4. Runtime configuration tab

Grouped cards:

- **Worker**: extension version, installed vs. default version, worker database, worker role,
  host, reconciliation interval, preloaded.
- **Starts and listing**: enable superuser instances, max new-transaction starts,
  new-transaction start timeout, list limit.
- **Connections**: max user / management / engine connections, execution acquire timeout.
- **Retention and logging**: retention days, log workflow SQL.

Missing GUCs show `—` with a "Not available in this version" tooltip.

Admonitions:

- `log_workflow_sql = on`: warning that fully substituted workflow SQL, including `$var`
  values, is written to Postgres logs, and turning it off requires a restart.
- `installed_version < default_version`: upgrade notice with a copyable
  `ALTER EXTENSION pg_durable UPDATE;` and the drain-before-upgrade warning (in-flight loops
  and waits may fail to replay).
- Installed version below 0.2.8: info notice listing which UI features are unavailable.

## 5. Re-run

### Reconstruction

Pure function `reconstructExpression(rootId, nodes): { expression } | { error }` in
`Durable.reconstruct.ts`. Walks from the root and emits pg_durable DSL text:

| `node_type`      | Source of fields                                             | Output                                                 |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------ |
| `SQL`            | `query` = SQL text                                           | `df.sql('…')`                                          |
| `THEN`           | `left_node`, `right_node`                                    | `df.seq(a, b)`                                         |
| `JOIN`           | left, right, `extra_nodes`                                   | nested `df.join(a, b)`                                 |
| `RACE`           | left, right                                                  | `df.race(a, b)`                                        |
| `IF`             | `condition_node` or `condition_type: result_has_rows` config | `df.if(c, t, e)` / `df.if_rows(name, t, e)`            |
| `LOOP`           | left body, `condition_node`, `continue_on_failure`           | `df.loop(body[, cond][, continue_on_failure => true])` |
| `SLEEP`          | `query` = seconds                                            | `df.sleep(n)`                                          |
| `SIGNAL`         | `signal_name`, `timeout_seconds`                             | `df.wait_for_signal(name[, n])`                        |
| `WAIT_SCHEDULE`  | `cron_expr`                                                  | `df.wait_for_schedule('…')`                            |
| `HTTP`           | `url`, `method`, `body`, `headers`, `timeout_seconds`        | `df.http(…)`                                           |
| `HTTP_MULTIPART` | `url`, `method`, `parts`, `headers`, `timeout_seconds`       | `df.http_multipart(…)`                                 |
| `BREAK`          | `break_value`                                                | `df.break([value])`                                    |

`result_name` wraps with `df.as(…, 'name')`. All strings are quoted with the same escaping as
`literal()`; JSON values are emitted as `'…'::jsonb`. Unknown node types, missing children,
unparseable config, or cycles return an error ("This workflow can't be reconstructed") — never
a guess. The exact IF-branch field mapping (left = then, right = else) is confirmed against
0.2.8 `node_status.rs` during implementation and covered by tests.

### Flow

- "Re-run" button in the detail sheet. Disabled with the same tooltip conditions as
  "Create workflow" (write permission, `can_start`, runtime configured).
- On click, reconstruct; on error show a toast with the reason. On success open
  `CreateWorkflowSheet` with `initialValues`: expression mode, reconstructed expression,
  original label, `transactionMode: 'caller'`.
- The sheet shows an admonition: `$var` references resolve against the **current**
  `df.vars`, not the original run's values; side effects (SQL writes, HTTP requests) run
  again.
- The user may edit, preview the plan, and then start. No one-click restart.

## 6. Cross-cutting

- New user-facing copy goes through the `copywriting` skill, wrapped in `$t(...)`, and is
  added to `apps/studio/lib/i18n/locales/zh-CN.json`.
- No hardcoded colors; semantic tokens only.
- Named exports only.
- Files stay focused: `Durable.utils.ts` (form schema + SQL generation),
  `Durable.tree.ts` (tree building, generation parsing), `Durable.reconstruct.ts` (re-run),
  `data/pg-durable/pg-durable.utils.ts` (capabilities).

## 7. Testing

Unit tests (vitest):

- `getDurableCapabilities`: below/at/above each threshold, pre-release suffixes, garbage input.
- SQL generation for every leaf and container type, `resultName` wrapping, `transaction_mode`
  only on `'new'`, capability rejection.
- Schema validation: each new rule, including top-level `break` rejection.
- `buildNodeTree`: THEN flattening, IF/LOOP conditions, JOIN extras, missing refs, cycles.
- Execution-id generation parsing.
- `reconstructExpression`: one fixture per node type using 0.2.8 node JSON shapes, nested
  combinations, `result_name`, and every error path.
- Existing `CreateWorkflowSheet.test.tsx` extended for a container step and the re-run
  `initialValues` path.

Gates: `pnpm --filter studio typecheck`, `pnpm lint --filter=studio` (lint ratchet must not
increase), `pnpm test:studio` for the Durable tests, `pnpm test:prettier`.

No browser end-to-end verification: no pg_durable 0.2.8 instance is available. This is a
known gap; reconstruction fidelity is covered only by fixtures derived from 0.2.8 source.
